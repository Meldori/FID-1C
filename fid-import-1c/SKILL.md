# Импорт 1С в Future IT Dent

Навык ведёт перенос клиники из 1С в Future IT Dent в три шага, и после каждого шага пользователь получает отчёт:

1. **Готовность** — цел ли файл, какая это 1С, всего ли хватает: «можно / можно с оговорками / нельзя».
2. **Загрузка** — сначала в тестовый тенант; в рабочий только по явному «да» пользователя и после дампа.
3. **Итог** — построчная сверка с 1С и счёт по каждой сущности: «Записи 803/803», общий «2 587/2 587 (100%)».

Механику (разбор XML, загрузку, сверку) делают скрипты из `scripts/`. Твоя работа — понять выгрузку конкретной клиники, при необходимости доработать импорт в коде FID и честно отчитаться. Загрузка без сверки ничего не доказывает: задачи импорта молча пропускают строку, если не нашли пациента или врача.

## Окружение

- Future IT Dent: `FID` (по умолчанию `C:/OSPanel/home/Future-IT-Dent`), PHP 8.5, MySQL 8.4 и Redis из OSPanel, Python 3, Git Bash.
- Для каждой клиники своя папка, например `C:/OSPanel/home/import-<клиника>/`: туда XML (`dump.xml`) и рабочая папка `work/` (`WORK`).
- Скрипты навыка: `scripts/` рядом с этим файлом. Запускай их по полному пути.
- Python-скрипты, читающие выгрузку клиента, запускай с `python -I`.

## Шаг 1. Готовность

1. Распакуй архив в папку клиники (на диске нужно в 3–5 раз больше размера XML).
2. Проверь файл: `python -I scripts/check_dump.py <dump.xml> --json <папка>/check.json`.
   Код 1 = повреждён (файл «начинается заново», обычно на отметках 4/8/12 ГиБ, или не закрыт тегом). Тогда реальные данные — только до первого повтора, а регистры (телефоны, цены, паспорта, графики) почти наверняка потеряны. Объясни это пользователю простыми словами и предложи новую выгрузку (см. `references/pitfalls.md`). Если пользователь всё же хочет грузить — вырежи целую первую копию: строки до последнего закрытого объекта перед повтором плюс `\t</V8Exch:Data>` и `</V8Exch:_1CV8DtUD>`.
3. Обзор: `python -I scripts/scan_1c.py <dump.xml> <папка>/scan` → `summary.md` (конфигурация, что есть, чего нет, вердикт) и `scan.json` (количества и примеры объектов).
4. Определи конфигурацию и прочитай её справочник:
   - `unf` → `references/config-unf.md` (Контрагенты, СтруктурныеЕдиницы, Событие, Прием, ПоступлениеДенежныхСредств);
   - `stom` → `references/config-stom.md` (Клиенты, Заявка, ОказаниеУслуг, ПриходныйКассовыйОрдер);
   - `unknown` → `references/explore.md`, изучай вручную.
5. Разбери XML по типам: из папки FID `php -d memory_limit=12G artisan tinker --execute="echo App\Services\Import\ImportFrom1CDBServices::get_from_1c('<dump.xml>', '<WORK>/');"` (2–3 минуты на гигабайт, запускай в фоне).
6. Сверь распределения значений в данных клиники с тем, что ждёт импорт (статусы записей, виды оплат, типы номенклатуры, виды цен, пометки удаления, группы контрагентов). Расхождения ищи по `references/explore.md`.

**Отчёт о готовности** — пиши пользователю в таком виде:

```
## Готовность выгрузки <клиника>: <МОЖНО / МОЖНО С ОГОВОРКАМИ / НЕЛЬЗЯ>
Файл: <целый / повреждён: где и что потеряно>
Конфигурация: <какая 1С>, период данных: <с … по …>
| Что | Есть в 1С | Сколько |  ← пациенты, сотрудники, услуги, цены, контакты, записи, счета, оплаты, паспорта, графики
Чего не будет в программе: <список и почему>
Что нужно доработать в импорте: <список или «ничего»>
Предлагаю: <загрузить в тестовый тенант <id> / сначала новая выгрузка>
```

Дальше не иди без ответа пользователя.

## Шаг 2. Загрузка

1. Если импорт нужно доработать — правь код FID (`references/explore.md`, раздел «Где что в коде»), минимально и так, чтобы не сломать другие конфигурации: новое поведение включай только когда в выгрузке есть нужный объект или поле.
2. Тестовый прогон с нуля:
   `WORK=<work> TENANT=<id> bash scripts/pipeline.sh`
   Скрипт пересоздаёт тестовый тенант (`<id>.localhost:8000`, подписка до 2222), собирает файлы, грузит их синхронно (почта в лог, внешние запросы запрещены), раскладывает записи по креслам и делает сверку. Ошибки каждого шага — в `<WORK>/errors_<шаг>.log`.
   Один прогон за раз: два параллельных задваивают счета и оплаты. Если прогон прервали снаружи, проверь, что не осталось процессов `fid_run.php`, и пересоздай тенант.
3. Разбери расхождения сверки (шаг 3), исправь, прогони снова. Повторяй, пока итог не станет полным или каждое расхождение не будет объяснено.
4. **Рабочий тенант** — только по явному согласию пользователя и по `references/transfer.md`: дамп базы, проверка, что сам тенант можно перезаписать, загрузка по шагам (`fid_run.php sync:<шаг> <tenant>`), раскладка по креслам, сверка. Повторная заливка поверх загруженного создаёт дубли счетов и оплат — только на откатанную из дампа базу.

## Шаг 3. Итог

```
php scripts/export_tenant.php <tenant | db:имя_базы> <WORK>/audit_<tenant>
python -I scripts/reconcile.py --work <WORK> --db <WORK>/audit_<tenant> --out <WORK>/reconcile_<tenant>.md --json <WORK>/reconcile_<tenant>.json
```

`db:имя_базы` — для дампа с сервера: подними его в отдельную локальную базу (`CREATE DATABASE …; mysql … < dump.sql`) и сверяй её.

`reconcile.py` пишет таблицу «В 1С / Загружено / Совпало / Итог» по пациентам, сотрудникам, услугам, записям, счетам и оплатам, суммы счетов и оплат и список расхождений с примерами. Код 0 — всё совпало.

**Итоговый отчёт** пользователю:

```
## Итог: <совпало>/<всего> (<процент>%)
<одна фраза: всё перенесено / есть расхождения — какие>
| Сущность | В 1С | Загружено | Совпало |
Деньги: счета <сумма 1С> / <сумма в базе>, оплаты <…> / <…>
Расхождения: <каждое — что, сколько, почему, нужно ли что-то делать>
Чего нет из-за самой 1С: <например, телефонов в повреждённой выгрузке>
Не проверено: <например, интерфейс в браузере>
```

Объясняй каждое расхождение: «4 записи — дубли в самой 1С, слиты в одну» — это норма; «1 сотрудник — ФИО в базе изменили вручную» — пусть решит пользователь; необъяснённое расхождение = импорт не готов.

## Правила безопасности

- В рабочий тенант (`lip`, тенант клиента на сервере) ничего не пишется без явного «да» пользователя в этом разговоре и без свежего дампа.
- Всегда отключены почта, рассылки и внешние HTTP-запросы на время загрузки: у пациентов настоящие email и телефоны.
- Решения про данные клиники (удалить «служебных пациентов», кого считать врачом, опекунов детей) принимает пользователь — ты показываешь факты и предлагаешь.
- Не утверждай «загружено 100%», пока не запущен `reconcile.py` и ты не прочитал его отчёт.
