# Импорт 1С в Future IT Dent

Навык ведёт перенос клиники из 1С в Future IT Dent в три шага. После каждого шага пользователь получает отчёт:

1. **Готовность**: цел ли файл, какая это 1С, всего ли хватает. Вердикт: «можно», «можно с оговорками» или «нельзя».
2. **Загрузка**: сначала в тестовый тенант. В рабочий тенант — только по явному «да» пользователя и после дампа.
3. **Итог**: построчная сверка с 1С и счёт по каждой сущности, например «Записи 803/803», общий «2 587/2 587 (100%)».

Всю механику делает одна команда: `scripts/fid1c.py` (Python 3.8+, только стандартная библиотека). Отчёты собирает тоже она, поэтому они одинаковые в любом ассистенте и без него. Твоя работа:
- понять выгрузку конкретной клиники;
- при необходимости доработать импорт в коде FID;
- запускать шаги, читать отчёты и объяснять пользователю каждое расхождение простыми словами.

Загрузка без сверки ничего не доказывает: задачи импорта молча пропускают строку, если не нашли пациента или врача.

## Как запускать

`<навык>` — папка этого файла. Команды запускай из папки клиники или с `-C <папка клиники>`:

```
python <навык>/scripts/fid1c.py <команда> [-C <папка клиники>]
```

На Linux/macOS вместо `python` пиши `python3`. Если ассистент запускает команды в PowerShell, синтаксис тот же.

| Команда | Что делает |
| --- | --- |
| `init <выгрузка.zip/.rar/.7z/.xml> --clinic "Название" --dir <папка> --test-tenant <id> [--timezone Europe/Samara]` | папка клиники, распаковка, `fid1c.json` |
| `doctor` | проверка окружения: PHP, Future-IT-Dent, MySQL, Redis, доработки импорта, mysqldump, место на диске |
| `readiness` | шаг 1 → `reports/readiness.md` |
| `load [--tenant <id>]` | шаг 2: пересоздать тестовый тенант, разобрать и загрузить, разложить по креслам, сверить → `reports/final_<id>.md` |
| `verify --tenant <id>` или `--db <база>` | шаг 3 отдельно: сверка уже загруженного или дампа с сервера |
| `chairs --tenant <id> [--count 4]` | разложить записи по креслам без наложений; `--count` — сколько кресел в клинике (или `"chairs"` в `fid1c.json`) |
| `backup --tenant <id>` | дамп базы тенанта перед переносом в рабочий |
| `extend --tenant <id>` | продлить подписку (`date_end`) |
| `status` | что уже сделано по клинике |

Коды выхода:
- `0` — успешно;
- `1` — есть проблемы или расхождения;
- `2` — ошибка в аргументах;
- `3` — окружение не готово;
- `4` — отказ по правилам безопасности. Это не ошибка, которую надо обойти: объясни причину пользователю;
- `5` — уже идёт другой прогон.

Долгие команды (`readiness` и `load` на гигабайтных файлах идут от 5 до 30 минут) запускай в фоне или с большим таймаутом. Не запускай вторую копию, пока идёт первая.

## Шаг 1. Готовность

1. `init` с архивом от пользователя. Затем `doctor`. Если Future-IT-Dent недоступен (например, ты в облачном чате без доступа к компьютеру), шаг 1 всё равно делается: `readiness --no-fid`.
2. `readiness` → покажи пользователю `reports/readiness.md` **целиком**, как есть.
3. Допиши в раздел «Комментарий» то, чего нет в цифрах. Для этого определи конфигурацию и прочитай её справочник:
   - `unf` → `references/config-unf.md`;
   - `stom` → `references/config-stom.md`;
   - `unknown` → `references/explore.md`.

   Примеры комментария:
   - служебные «пациенты»;
   - нет часового пояса;
   - необычные статусы или виды оплат.

   Примеры полей лежат в `reports/scan/scan.json`. Распределения значений смотри после `parse` в `work/V8Exch_Data/*.json` (см. `references/explore.md`).
4. Если файл повреждён, объясни простыми словами, что потеряно, и как сделать новую выгрузку (`references/pitfalls.md`).

Дальше без ответа пользователя не иди.

## Шаг 2. Загрузка

1. Если `readiness` или `doctor` говорят, что импорт нужно доработать, правь код FID по `references/explore.md`:
   - минимально;
   - новое поведение включай только по наличию объекта или поля в выгрузке, чтобы не сломать другие конфигурации.
2. Для Стоматологической клиники узнай у пользователя часовой пояс филиала и запиши его в `fid1c.json`: `"timezone": "Europe/Samara"`.
3. `load` — тестовый прогон с нуля. Тенант с меткой fid1c пересоздаётся. Тенант, созданный не fid1c, пересоздаётся только с `--adopt`, и только когда пользователь подтвердил, что он тестовый.
4. Разбери расхождения итога (шаг 3), исправь и прогони `load` снова. Повторяй, пока итог не станет полным или каждое расхождение не будет объяснено.
5. **Рабочий тенант** — только по `references/transfer.md`: явное «да» пользователя в этом разговоре, `backup`, затем `load --tenant <id> --production --backup <дамп> --yes`. Команда сама откажется, если:
   - дамп старше 3 часов или неполный;
   - в тенанте уже есть загруженные данные.

## Шаг 3. Итог

`load` заканчивается сверкой сам. Отдельные варианты:
- `verify --tenant <id>` — сверить уже загруженный тенант;
- `verify --db <база>` — сверить дамп с сервера, поднятый в отдельную локальную базу;
- `verify --work <папка с V8Exch_Data> --export <папка выгрузки базы>` — сверить по готовым файлам, без Future-IT-Dent (например, в облачном чате).

Покажи пользователю `reports/final_<id>.md` целиком и допиши «Комментарий»: каждое расхождение — что это, сколько, почему, нужно ли что-то делать. Как понимать расхождения:
- «4 записи — дубли в самой 1С, слиты в одну» — это норма;
- «1 сотрудник — ФИО в базе изменили вручную» — пусть решает пользователь;
- необъяснённое расхождение значит, что импорт не готов.

В отчёте есть раздел «Метрики»: пациенты, счета, оплаты наличными и безналом, записи по месяцам и статусам, расстановка по креслам. Каждая метрика — пара «в 1С / в базе». Строка с ✘ — расхождение: объясни его так же, как расхождения сверки.

Подробный разбор лежит в `reports/reconcile_<id>.md` и `.json`, ошибки загрузки — в `work/errors_<шаг>.log`, полный журнал — в `logs/`.

## Правила безопасности

- В рабочий тенант (`protected_tenants` в `fid1c.json`, по умолчанию `1` и `lip`) ничего не пишется без явного «да» пользователя и свежего дампа. Скрипт это проверяет; не обходи проверки правкой `fid1c.json` или ключами без согласия пользователя.
- Почта, рассылки и внешние HTTP-запросы на время загрузки отключены: у пациентов настоящие email и телефоны.
- Решения про данные клиники принимает пользователь: удалить ли служебных «пациентов», кого считать врачом, кто опекун детей. Ты показываешь факты и предлагаешь.
- Не утверждай «загружено 100%», пока не прочитал `final_<id>.md`.
- Выгрузки клиник — персональные данные пациентов. Не копируй их в репозитории и не отправляй в сторонние сервисы.
